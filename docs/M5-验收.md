## 3. 性能预算（开发任务书 §12）

| 指标 | 目标 | 实测 | 判定 |
|------|------|------|------|
| 冷启动到可交互 | < 1.5 s | 后端就绪 **0.67 s**（二次启动）；首次含建表迁移约 1.65 s | 达标（后端） |
| 空闲内存（专用提交） | < 120 MB | 主进程 7.1 MB + WebView2 六进程 200.4 MB ≈ **207.5 MB** | **未达标**（见 §4） |
| 播放中内存 | < 180 MB | 同上量级（WebView2 固有开销主导） | **未达标** |
| 安装包 | < 15 MB | 单文件 exe **7.75 MB** | 达标 |
| 安装后磁盘占用 | < 50 MB | exe 7.75 MB + SQLite（随订阅增长），远小于 50 MB | 达标 |
| 1 万集列表滚动 | 稳定 60 fps | 虚拟滚动（`@tanstack/virtual-core` 手写窗口化，实测 500 集仅渲染 14 行） | 达标（机制） |
| 订阅 20 频道刷新 | < 15 s（并发 3） | M3 实测 21/21 源 **9.6 s**，二次刷新 0 新集（ETag 命中） | 达标 |

> 冷启动口径：Tauri tracing 日志时间戳，从「启动」到「数据库就绪」。前端为静态 SPA，
> 后端就绪后 WebView 渲染到可交互几乎无额外阻塞，故后端就绪时间可近似代表冷启动。
> 内存口径：Windows「专用提交」(PrivateMemorySize64)，按 `--user-data-dir` 精确归属到本应用的
> 6 个 WebView2 子进程；「工作集」(WorkingSet) 会把共享 DLL 页在每进程重复计入，虚高到约 430 MB，
> 不用于判定。

## 4. 与任务书的偏差 / 已知限制

| 项 | 任务书 | 实际 | 原因与建议 |
|----|--------|------|-----------|
| 空闲/播放内存 | < 120 / 180 MB | 专用提交 ≈ 207 MB | **WebView2(Chromium) 多进程引擎固有开销**（browser/gpu/renderer/utility×2/crashpad 六进程）。这是架构选型（§3 要求 WebView2 + Tauri）与内存预算的内在矛盾：Tauri 主进程只有 7 MB，但 WebView2 runtime 起步就 ~200 MB。压到 120 MB 需换渲染方案（自绘 / Ultralight），成本极高。**建议：接受当前开销，或将预算口径改为「主进程 + 应用自有数据」** |
| NSIS 安装包 | 出安装包 | 未产出 | 构建机下载 NSIS 3.13 工具链被网络代理拦截（502），与 M0 同一问题。网络可达 GitHub 时重跑 `pnpm tauri build` 即可 |
| 自动更新服务端 | GitHub Releases | 端点已配，未发布版本 | 需先建仓库 `haha-anything/dear-universe-podcast` 并发布带 `latest.json` 的 Release，端点与签名公钥已写入配置，发布后即可用 |
| 冷启动首次 | < 1.5 s | 首次含迁移 1.65 s | 仅首次建库时略超，二次启动 0.67 s，可接受 |
